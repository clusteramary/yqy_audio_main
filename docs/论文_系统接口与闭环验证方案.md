# 系统接口与闭环验证方案

版本：2026-10-08。本文是第五章设计稿和后续实现契约；表中“拟新增”尚未接入运行代码。现有实现参见 `interview_robot/state.py`、`runtime.py`，神经模型当前离线运行。

同日续开发：新增独立 `confirmed_runtime.py`，请求ID、确认关联、超时故障、人工恢复及日志已在纯本地控制器中实现，Cross-Encoder 已有运行时排序适配器。具体可运行范围见 [交付记录](本地持续开发交付_2026-10-08.md)。下文“待实现”属于先前设计状态；真实设备、情感输出消息、动作完成反馈、服务层可中断超时及低质量拒选仍未实现。

## 1. 现有流程与边界

规则状态估计接收带时间戳的文本、音频、视觉观测。当前用户发声或 ASR 尚未结束时保持 HOLD；只有检测到发声之后足够长的静音并收到最终文本，才输出 SHIFT。音频缺失不能直接当静音。播放活动优先进入 ROBOT 状态。

控制器收到允许接话的状态后，从尚未问过的文本候选中选择一项，进入 PROCESSING。检测到机器人播放后转为 SPEAKING，随后进入 COOLDOWN。当前只支持操作员显式 `cancel_pending()` 恢复，没有基于请求 ID 的确认关联和自动超时管理，不能宣称已容忍乱序/丢失反馈。

现有 `LegacyKeywordAdapter` 将已知动作关键词映射到动作索引，默认 dry-run。UDP 发送成功只说明本地发送操作完成，不证明对端接受或实际动作完成。论文用语应为高层动作索引调度，不能称为已完成底层轨迹规划。

## 2. 拟新增接口契约

| 消息 | 必填信息 | 接收方检查 |
| --- | --- | --- |
| Observation | session_id、utterance_id、采集时间、可用性、最终转写标志 | 同会话、严格时间顺序、观测是否过期 |
| EmotionEstimate（拟新增） | 输入话语ID、模型/特征版本、标签顺序、概率、有效模态、起止推理时间 | 概率有限且和为1；不把类别等同接话意愿 |
| RankResult（拟新增） | 历史截止ID、候选ID及版本、知识版本、分数、所选ID、起止时间 | 不含未来；所选ID属于本次候选；无候选时不输出伪问题 |
| SpeechRequest（拟新增） | 唯一request_id、会话、话语、问题文本、发送时间 | 同一请求幂等，未完成请求不重复发声 |
| PlaybackEvent（拟新增） | request_id、事件序号、started/finished/failed、发生时间 | 只接受当前请求匹配事件，重复事件不推进状态 |
| ActionEvent（拟新增） | request_id、动作索引、接收/完成/失败事件 | 无完成反馈时记录unknown，不写成功 |

日志以统一单调时钟记录同一进程内耗时，另保留 UTC 墙钟用于定位。跨进程或设备时钟没有同步保证时，不直接相减得到端到端延迟；分别记录本地往返时间和远端内部时长。每条日志保留 schema_version，便于迁移。

## 3. 拟新增故障策略

在 PROCESSING 等待开始确认超时，进入明确的 FAULT 状态，记录当前请求和超时原因；不立即自动重发同一句，因为确认可能丢失而声音已播放。恢复需要查询播放端状态或操作员明确处理。SPEAKING 缺结束确认也进入故障处理，不能仅按预测 TTS 时长推定播放结束。

只有匹配当前 request_id 的 started/finished 事件才能推进状态。过期、重复和其他会话事件单独计数。人工恢复保留原请求已发送事实与去重记录；是否允许重新提同一问题应通过新请求显式指定，不能偷偷清空所有历史。

这些策略首先做纯本地回放，不连接机器人端口。接口稳定后再增加设备适配器和实际播放确认，避免将测试故障触发到真实设备。

## 4. 无服务器回放验收矩阵

| 场景 | 输入事件 | 期望行为 | 当前证据 |
| --- | --- | --- | --- |
| 正常交互 | 用户发声→静音/最终文本→播放→结束 | 单次发问，播放等待，结束冷却 | 已有基本规则和测试；非实机结果 |
| 采集缺失 | 无音频但ASR结束 | 不将缺失当静音接话 | 已有规则 |
| 待确认 | 选择问题后未出现播放状态 | 不重复 ASK | 已有 PROCESSING 等待 |
| 开始确认丢失 | 请求已发送无 started | 超时故障，不自动重复发声 | 待实现 |
| 结束确认丢失 | started 后无 finished | 故障日志及明确恢复 | 待实现 |
| 旧/重复确认 | 请求A结束事件到达请求B | 不改变B的执行状态 | 待实现请求关联 |
| 候选耗尽 | 无未问过候选 | 等待补充，不重复旧问题 | 已有精确文本去重；非语义去重 |
| 全部低质量候选 | 有候选但无合理追问 | 澄清/等待，记录原因 | 待实现拒选策略 |
| 模型异常 | 超时、非有限分数、版本不匹配 | 保守回退并记录异常 | 待实现在线适配 |

回放结果用于说明软件状态约束，不作为实际回声消除、网络鲁棒性或用户体验证据。

## 5. 前两点如何形成可检验联系

第一阶段只把两个模型的结果接入统一日志，检查会话与话语 ID 对齐，不让情绪类别直接控制动作。第二阶段固定追问排序器，比较是否使用可靠情感输出的高层策略；策略和阈值只在开发会话确定。第三阶段结合真实参与者反馈判断这种使用方式是否有益。

如果点一只有离线 MELD 证据，点二只有离线 KdConv 证据，系统只能报告模块集成演示。不能将两个数据集的不同人物拼成同一会话，更不能由两个离线分数相加推导端到端收益。

## 6. 设备试点与用户实验设计

先做少量内部设备试点，测量可完成率、播放确认时延、意外插话与异常恢复；试点用于修正协议，不与正式参与者数据混报。保存失败尝试及退出原因。

拟比较规则系统、仅启用情感相关策略、仅启用学习式追问、组合系统。参与者内比较时平衡条件顺序和话题，避免所有人先体验规则再体验完整系统。每个条件保持相近对话时长、候选资源和动作能力；若改变这些因素，应单独说明。

主要系统指标：从最终话语可用到播放开始的时间、未确认请求比例、重复发问、意外插话、任务完成情况。体验指标可包含相关性、自然度和交流负担，但题目与量表需在试点后固定。统计单位以参与者或会话为主，不能把同一人的每一句当独立参与者。

正式人数尚未确定。先根据试点方差、实际可招募人数和研究目的确定，不提前承诺显著性。录音录像、匿名ID、保存期限和撤回方式应明确告知参与者，并遵循学校对人机实验的要求。
